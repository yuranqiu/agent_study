## 1. 核心原理与索引算法

### 1.1 向量检索的本质

向量检索的核心是在高维空间中找到与查询向量最相似的 Top-K 个向量。直接计算所有向量距离的时间复杂度是 O(N)，无法满足大规模数据的需求。

**相似度度量方式**：

| 度量方式 | 公式 | 适用场景 |
|---------|------|---------|
| **Cosine Similarity** | cos(θ) = (A·B)/(\|A\|\|B\|) | 文本 Embedding（方向更重要） |
| **L2 Distance** | \|\|A - B\|\|₂ | 图像特征、特征含义重要 |
| **Dot Product** | A·B | 归一化后的向量、推荐系统 |

### 1.2 HNSW（Hierarchical Navigable Small World）

HNSW 是目前最流行的向量索引算法，通过构建多层小世界图实现近似最近邻检索。

**核心思想**：
- 构建多层图，上层稀疏、下层密集
- 检索时从顶层开始，逐步下探
- 每层都是小世界网络：局部稠密、全局稀疏

```python
# HNSW 参数说明
parameters = {
    "M": 16,           # 每层每个节点的最大连接数（影响召回率和内存）
    "efConstruction": 200,  # 构建时的动态列表大小（影响召回率和索引时间）
    "efSearch": 100,   # 检索时的动态列表大小（影响召回率和延迟）
    "level_mult": 1.0, # 层间衰减因子
}
```

**参数调优指南**：

| 参数 | 增大时的效果 | 代价 |
|------|-------------|------|
| M | 召回率↑、内存↑ | 索引体积增大、索引时间增长 |
| efConstruction | 召回率↑、召回率↑ | 索引时间显著增长 |
| efSearch | 召回率↑ | 检索延迟增加 |

**适用场景**：通用场景，内存充足时首选

### 1.3 IVF（Inverted File Index）

IVF 将向量空间划分为多个聚类，检索时只搜索最相关的几个聚类。

```python
# IVF 参数说明
parameters = {
    "nlist": 1024,     # 聚类数量（建议 4*sqrt(N) ~ 4*sqrt(1000000) ≈ 2000）
    "nprobe": 32,     # 查询时搜索的聚类数量（影响召回率）
}
```

**召回率 ≈ nprobe / nlist**，nprobe 越大召回率越高，但延迟也增加。

**适用场景**：数据量大、内存有限、可以接受较低召回率的场景

### 1.4 PQ（Product Quantization）

PQ 将高维向量分割成多个子向量，分别进行聚类编码，大幅降低存储成本。

```python
# PQ 参数说明
parameters = {
    "m": 8,            # 分段数量（d/m 个子向量一段）
    "nbits": 8,        # 每个子向量的编码位数（2^8=256 个聚类中心）
    "nlist": 256,      # 子向量的聚类数
}
```

**压缩比计算**：
- 原始存储：D × 4 bytes（float32）
- PQ 存储：D/m × nbits bits
- 压缩比 ≈ (4×m) / nbits

例如 D=768, m=8, nbits=8 → 压缩比 ≈ 4:1

**适用场景**：超大规模数据、内存严重受限、对精度要求不极端高的场景

### 1.5 HNSW + IVF 混合

很多生产系统会组合使用：

```python
# PostgreSQL pgvector 的组合索引
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 200);

# Qdrant 的 HNSW +_payload
# HNSW 负责向量检索，payload index 负责标量过滤
```

### 2.3 详细对比

#### Milvus

**优点**：
- 功能最全面，支持多种索引类型
- 分布式架构成熟，支持水平扩展
- 社区活跃，文档完善
- 支持 GPU 加速（HNSW）

**缺点**：
- 架构较重，小规模场景 overhead 大
- 运维复杂度高
- 某些功能需要企业版

```python
# Milvus Python SDK 示例
from pymilvus import connections, Collection, FieldSchema, CollectionSchema, DataType

# 连接
connections.connect(host="localhost", port="19530")

# 定义 schema
fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=768),
]
schema = CollectionSchema(fields, "my_collection")
collection = Collection("my_collection", schema)

# 插入数据
entities = [
    [i for i in range(1000)],  # id
    [[0.1] * 768 for _ in range(1000)]  # embeddings
]
collection.insert(entities)

# 检索
search_params = {"metric_type": "COSINE", "params": {"ef": 100}}
results = collection.search(
    data=[[0.1] * 768],
    anns_field="embedding",
    param=search_params,
    limit=10
)
```

## 3. 性能与精度权衡

### 3.1 召回率 vs 延迟

向量检索是召回率和延迟的权衡。HNSW 的 ef 参数是核心调优点：

```python
# efSearch 对召回率和延迟的影响（Milvus 实测）
benchmark_results = {
    "ef=50":  {"recall": 0.85, "p99_latency_ms": 5},
    "ef=100": {"recall": 0.92, "p99_latency_ms": 10},
    "ef=200": {"recall": 0.96, "p99_latency_ms": 20},
    "ef=500": {"recall": 0.98, "p99_latency_ms": 50},
}
```

**经验法则**：efSearch 设置为 2-4 倍的目标召回 Top-K 数

### 3.2 索引类型选择

| 数据规模 | 推荐索引 | 原因 |
|---------|---------|------|
| < 10K | 暴力搜索（brute force） | 无需索引，直接计算最快 |
| 10K - 1M | HNSW | 召回率高，延迟可控 |
| 1M - 10M | HNSW + 适当参数 | 需要调优 M 和 ef |
| > 10M | IVF-PQ 或 DiskANN | 内存限制，需要量化压缩 |

### 3.3 精度损失控制

PQ 会引入量化误差，控制方法：

1. **增大 m**（更多分段）：精度↑，但存储和计算增加
2. **增大聚类数**（增大 nbits）：精度↑，但存储增加
3. **OPQ（Optimized PQ）**：训练时对向量做旋转，减少量化误差

```python
# Milvus 中配置 PQ + OPQ
index_params = {
    "index_type": "IVF_PQ",
    "metric_type": "COSINE",
    "params": {
        "nlist": 1024,
        "nprobe": 64,
        "m": 8,
        "nbits": 8
    }
}

# 启用 OPQ
index_params["params"]["opq_enabled"] = True
```

### 3.4 批处理 vs 实时检索

**批处理场景**（离线、向量化文档）：
- 可以接受更长延迟
- 追求高召回率
- 加大 efConstruction、加大 M

**实时检索场景**（在线、用户请求）：
- 需要极低延迟（< 50ms）
- 召回率可以适当降低
- 优化 efSearch，启用缓存

### 5.4 容量规划

```python
# 容量估算公式
def estimate_capacity(num_vectors, dim, index_type="HNSW"):
    # 原始数据大小
    raw_size_gb = num_vectors * dim * 4 / (1024 ** 3)
    
    if index_type == "HNSW":
        # HNSW 索引约为原始数据的 1-2 倍
        index_size_gb = raw_size_gb * 1.5
        overhead_gb = raw_size_gb * 0.2  # 操作开销
    elif index_type == "IVF_PQ":
        # PQ 可以压缩到 1/4 - 1/8
        compression_ratio = 0.125
        index_size_gb = raw_size_gb * compression_ratio
        overhead_gb = raw_size_gb * 0.1
    
    total_gb = raw_size_gb + index_size_gb + overhead_gb
    
    # 推荐预留 50% buffer
    recommended_gb = total_gb * 1.5
    
    return {
        "raw_size_gb": round(raw_size_gb, 2),
        "index_size_gb": round(index_size_gb, 2),
        "total_gb": round(total_gb, 2),
        "recommended_gb": round(recommended_gb, 2)
    }

# 示例：10M vectors，768维，HNSW
estimate_capacity(10_000_000, 768, "HNSW")
# {'raw_size_gb': 28.84, 'index_size_gb': 43.26, 'total_gb': 49.42, 'recommended_gb': 74.13}
```

### 5.5 常见问题与解决方案

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| **检索延迟突然升高** | 索引合并 / 内存不足 | 监控内存，增加副本分散负载 |
| **召回率下降** | efSearch 过低 / 数据漂移 | 增大 efSearch，定期重建索引 |
| **插入速度慢** | 批量写入配置不当 | 增大 batch size，使用 bulk API |
| **OOM** | 索引配置过于激进 | 降低 M/efConstruction，使用 PQ 压缩 |
